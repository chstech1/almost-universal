# Live entity state on the handheld

At 4:11:26.418 p.m. EST on November 20, Home Assistant showed `climate.home` available in `heat_cool`, with `current_temperature: 68` and `temperature_unit: °F`. The Climate proof reads that attribute from the current Home Assistant state. No thermostat service is involved.

## Read-only exchange

Opening a screen starts one subscription for its predefined fields. Home Assistant reads current values and sends a full snapshot. Subsequent deltas contain only changed fields. Closing the screen clears its subscription. After reconnect, the handheld opens a new subscription and waits for a new snapshot before showing values as current. A gap in delta sequence requires a fresh snapshot. If the handset keeps a reading after the link drops, it labels it **Last known**. An explicit unavailable field clears the number.

The offline implementation matches the [DSP logical frame specification](../firmware/dsp-v48/PROTOCOL.md#proposed-screen-snapshots-and-state-updates). It starts snapshots at sequence zero, echoes the screen and subscription ID, and uses the same projection for booleans, scaled numbers, enumerations, and temperatures with explicit units. The handset cannot supply an entity ID. Home Assistant owns the screen-to-field map. Climate is the only real entity in the prototype. Tests use synthetic light, cover, and fan states.

The session coalesces state changes to their latest values. It stays within eight fields per screen and 64 bytes per logical frame, with updates at least 250 ms apart and one send in flight. A verified carrier may need smaller messages or a slower rate. Its adapter will own the scoped HA state listener and the monotonic flush timer. Replace the listener when the selected screen changes and release it on close or disconnect. Never requeue a reply on a different peer or activation.

## Firmware gate

The repository's TV A build stays at 0.1.3. The offline patch adds a session factory and accepts a simulated sender for tests. The stock GATT handlers do not call it. A verified inbound carrier must deliver the logical payload over the same normal v4.8 session, with a reliable connection generation and bounded DSP RAM use. The current version handshake alone does not prove that capability. Verify the no-persistence behavior and physical readback before building a Climate firmware package or enabling any new write.

First prove the Climate snapshot against the Home Assistant States view and then a delta from a naturally changing room reading or an isolated simulator. Compare both value and unit. Verify Back, loss of link, and reconnect with a fresh snapshot. Confirm that the existing TV A binding still works under its original key-report contract.

### Which stock inputs are actually available

“Unused” has three distinct meanings in the shipping binaries. An ARM command can return unsupported, a registered DSP callback can discard its input, or a number can be absent from one registration table. Only the first two are evidenced behaviors. None establishes a vendor-reserved extension point.

| Candidate | Evidence in the archived v4.8 members | Consequence |
|---|---|---|
| Explicitly unsupported ARM cases | The normal extension dispatcher recognizes six families and returns status 5 for other families. In the sync/profile family, case 8 explicitly returns status 5. Two subcases of case 4 do the same. | These cases terminate on ARM. They provide a stock rejection baseline for a future compatibility test. No private command number is assigned here. |
| Registered DSP no-op | The application registers tag 3 with the callback pointer at DSP member offset `+0x5c9c`. ### Minimum application change to prove offline

Start with **one snapshot on opening Climate**. HA reads only `climate.home.current_temperature` and the unit. The remote displays a reading taken on entry or an unavailable indicator. Back discards it. Returning to Climate requests a fresh snapshot. This first proof establishes delivery without claiming continuous freshness or a supported update frequency.

1. **Identify compatible endpoints.** Require affirmative capability evidence from the modified ARM and a matching DSP request on the active HA connection before HA sends a value. A stock v4.8 version reply alone is insufficient. Stock ARM with either DSP keeps its existing operations. Modified ARM with stock DSP, no HA, a different peer, or a missing capability leaves the extension dormant. Establish a reliable connection-generation signal and the normal session's peer authorization before enabling replies. The existing version exchange establishes connectivity only.
2. **Add one bounded normal application handler.** Scope it to the existing normal parser after its session checks. Accept a single Climate snapshot for the outstanding view, with the existing logical schema: exactly 18 bytes for the typed reading or 15 for unavailable. Validate the complete length, one field, unit, range and subscription before copying. Own one fixed-size RAM record at most. Expose only that operation; sender-selected entities, service calls, pointers, flash destinations and opaque forwarding are outside the contract. The app owns no new persistent setting.
3. **Deliver only to the active DSP.** Allocate a distinct application message only after proving namespace and RAM ownership on both cores. Copy the validated record once to a receiver that schedules the display update on the UI task. Bound the number in flight to one. If the DSP is busy or asleep, release the record and let the visible view request another snapshot. Invalidate outstanding work on Back, disconnect, sleep, reset and mode change. The stock general-purpose sender can wake the display and queue payloads, so its ready, buffer-lifetime and timeout behavior needs an independent proof before reuse. A BLE write acknowledgment is insufficient evidence of rendering.
4. **Keep other paths independently testable.** Preserve stock behavior for all other normal operations, unknown commands, Office/TV key notifications, app-origin OTA entry, physical KATA entry and cold boot. With a stock DSP, the retail UI must still start. With a custom DSP and HA offline, the existing local menu must still work. Entering update mode disables the relay and clears its RAM state. The retail updater must be reachable without running the Climate handler or receiving a DSP capability message. KATA entry itself executes ARM application code, so retaining its bytes cannot guarantee recovery if the modified application fails before reaching them. Open questions before an ARM trial include custom ARM boot acceptance, a collision-free operation and IPC assignment, a safe fast path when the DSP is already awake, reliable session invalidation, space on both cores and application-independent restoration on V06. ### Wireless relay and 100 KiB transfer target

Start with an opt-in handler in the exact v4.8 ARM application. Use the existing normal BLE connection and add one request-bound Climate reply. Preserve the reset entry, KATA check, recovery service, OTA writer, resident DSP loader and boot metadata. The stock updater has two ARM destinations and verifies the new image before switching banks. A successful image CRC proves the staged bytes. A recoverable trial also requires a demonstrated path to the untouched stock bank when the candidate fails before application startup, or a separate verified MCU restore. A timed reset alone can select the same failed bank again. [Stock OTA and bank commit](firmware.md#bluetooth-recovery-uploader)

Treat 100 KiB as the maximum assembled object size. For bulk transfers, use explicit framing with small flow-controlled chunks in normal mode. A 512-byte application payload is a design example and may span BLE writes. At that size 100 KiB takes 200 chunks. Acknowledge data at the DSP, bound the number of chunks in flight, and let button events and live state take priority. The stock short-command reassembler waits about one second per separately dispatched command, so bulk transfer needs a different completion boundary. For files, stage and verify a temporary file with the DSP's existing LittleFS, then activate the new version only after validating its length, digest and format. Retain the previous valid version until commit. Pre-size or decode artwork in tiles.

The 16 MiB U6 provides storage capacity. A test on an archived LittleFS copy accommodated 1 MiB of additional content, while live free space and sustained device-side writes remain unmeasured. The exact v4.8 DSP has a 170 KiB LVGL arena before allocations. The largest free block with the menus active and the ARM's working RAM headroom remain unmeasured. Size the relay around a small bounded window and budget decoded pixels independently of the transfer size.

The offline Climate relay proof now connects the isolated HA provider to the logical DSP decoder and the archived Office renderer through a modeled ARM operation. It verifies separate Fahrenheit, Celsius and unavailable snapshots, stale delivery after Back and reconnect, and forbidden frames. A separate run of the retail ARM extension dispatcher returns unsupported for the logical snapshot. Physical transport and independent recovery remain open.

The normal parser placement and V06 recovery report follows the same snapshot through retail reassembly and normal dispatch, compares a simulator-only ARM extension, and checks the compact-header renderer. It records the 100-callback completion boundary, URM1 reuse for menus, separate artwork transfer requirements and the outstanding independent recovery evidence.

An offline stock-ARM test also carried a single value through the SwitchBot app's sync-completion path to a modeled DSP observer and the actual Climate renderer. The same observer displayed an older queued temperature after Climate reopened and interpreted a normal two-item sync as a temperature. The message lacks the source and view identity needed to accept it as current. The stock sender can also wake or queue work and acknowledge a dropped value. Treat the one-byte result as transport evidence. A DSP-only trial needs a way to distinguish a reply for the active view while preserving stock sync behavior. The operator reports that the chip pins are inaccessible and a wired ARM loader connection has been unsuccessful on the exposed pads. The bench uses stock ARM.

The follow-up simulator carried a 32-bit request ID, availability and unit, signed tenths, and a checksum in 16 ordered completions. A different request ID rejected an old reply. Reusing the ID after a restart accepted the old reply. The retail sender also canceled a pending idle countdown before delivery. The timer implies a nominal quiet window of about one second per command. Keep this proof offline while request identity and stock sync effects remain unresolved.

For now-playing art, the report sizes sample thumbnails and traces stock chunks of up to 768 bytes. The verified normal sender of those chunks commits a configuration table to ARM flash. A live artwork path needs independently verified bulk delivery and a bounded display decoder.

The labeled DSP_RX pad is a separate potential wired bench path. The compact-header DSP retains the stock UART initialization and receive callback. A bounded observer could copy bytes the callback already receives and hand a complete sample to the UI task. The bench confirmed DSP_TX at the startup rate. DSP_RX connectivity, levels, application-rate delivery and buffering remain to be verified. A successful UART trial would prove an independent DSP data path with the stock ARM in place. A wireless handheld would still need its own link.
